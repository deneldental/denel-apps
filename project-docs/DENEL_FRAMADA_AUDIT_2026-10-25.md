# Denel ↔ Framada audit — verified findings and implementation plan

**Original audit:** 25 October 2026 (a comparison of packaged Denel and Framada snapshots)
**Verification pass:** 25 October 2026. Every finding was traced again in the current working tree, then corrected and extended.
**Status:** ready to implement one step at a time (§8). All owner decisions were made on 26 October 2026 (§7). Neither pass changed application code, ran migrations, wrote to a database, deployed or sent messages.
**Scope:** `portals/` and `backend/`, which are the project's current focus (CLAUDE.md, `denel-rebrand-plan.md`). Problems found in the other apps are recorded in §11 but not scheduled.
**Evidence bundle from the original audit:** `C:\Users\Melarc.py\Downloads\DENEL_FRAMADA_AUDIT_2026-10-25\` (`comparison-inventory.json`, `evidence/`).

## How to use this document

- Work through §8 from top to bottom. Each step is one bounded slice. It lists its findings, the owner decisions it needs (§7), the tests to write first, and an exit check.
- Every finding keeps a stable ID: F01–F14 come from the original audit and F15–F25 are new. Put the ID in test names and change notes.
- **Confirmed** means the mismatch between caller, handler and configuration was re-read in today's source. It does not mean a browser or database run reproduced it, unless the entry says **executed**.
- The rule for every fix: write the failing test first and watch it fail on the current code. Then fix, watch it pass, and re-run the full suite. Where a protection matters, prove the test can fail by temporarily breaking the protection.
- Do not bulk-merge Framada. Port only the slices named here, and keep Denel's own work (§6).

### 1.4 What this pass ran, and what it did not

Ran (each needs no database):

- **Snapshot hash comparison** of both trees against `comparison-inventory.json` (§1.1).
- **Strict contract audit:** a copy of `scripts/api-contract-audit.mjs` in which a `${…}` hole can only match a parameter segment, never a literal. It also scans `patient/` and `reports/`. Results: portal 1 (F05), patient 0, HR 4 false positives (dynamic resource names), reports 12 (§11).
- **Route guard sweep:** every backend handler with no recognisable permission guard, following local and library helper functions. 157 handlers were flagged. All non-public ones were reviewed by hand. Public token, self-service and device routes are intentional. The real gaps are F01, F22 and F23.
- **Better Auth input probe:** the installed library's own `parseUserInput`, run with the app's exact `user.additionalFields` and plugins (Appendix A). `{"roleId":"admin"}` is accepted and `{"role":"admin"}` is rejected.

Not run: unit, integration or browser suites; database failure injection; an end-to-end HTTP request for F15 (it needs a real session and writes the user row); deployed configuration or data.

### Step 1 — privilege escalation

#### F15 — Any signed-in staff user can make themselves admin — P0 (new)

**Who:** every account with a Better Auth session: receptionist, doctor, Team-app `staff` and `lab_technician`, HR `hr_admin` and `external_trainer`.

**Evidence:**
- `backend/src/auth.ts:76-87` declares `roleId` and `phone` as `user.additionalFields` without `input: false`.
- In Better Auth 1.6.2, `POST /api/auth/update-user` (`backend/node_modules/better-auth/dist/api/routes/update-user.mjs`) writes every additional field that `parseUserInput(…, 'update')` lets through. Only fields marked `input: false` are refused (`dist/db/schema.mjs:34-84`). The admin plugin locks `role`, `banned` and similar fields that way. `roleId` is not locked.
- **Probe (executed, no database, Appendix A):** with the app's field configuration plus `admin()` and `username()`, `{"roleId":"admin"}` is accepted, `{"phone":…}` is accepted, and `{"role":"admin"}` is rejected with "role is not allowed to be set".
- Nothing intercepts the request. `backend/src/app.ts` forwards every `/api/auth/*` path that is not in `CUSTOM_AUTH_PATHS` to Better Auth. `enforceInterfaceScope` skips `/api/auth`. The CSRF middleware skips `/api/auth/*`, and Better Auth's own origin check passes because the user calls from their own app's origin.
- `backend/src/rbac/engine/PermissionEngine.ts:77` returns allow for `user.roleId === 'admin'`, read from the database row. Scope checks also resolve from `roleId`, so the account gains portal and HR access. `backend/src/rbac/session-cache.ts:183` drops the session cache after `/update-user`, so the change takes effect on the next request.

**Impact:** full RBAC takeover from any staff account, covering every patient record, payment, payroll item, setting and integration. Self-editing `phone` matters less (it is used for doctor contact and display) but should be locked too.

**Not run (original audit):** an end-to-end request. Every hop was confirmed by the probe or by reading the source.

**Executed on 2026-10-26 (Step 1), end to end:** a receptionist signed in through the real `/api/auth/sign-in/email`, sent `POST /api/auth/update-user {"roleId":"admin"}`, and Postgres held `roleId = 'admin'` afterwards. With that row, the same session got **HTTP 200 from `GET /api/users`** (403 before). The same request also rewrote `phone`, **`username` (the staff-ID sign-in handle) and `displayUsername`**, which the original finding missed: the username plugin's fields are client-writable and cannot be locked from `additionalFields`. `role`, `banned`, `emailVerified` and `email` were already refused.

**Status: FIXED in Step 1 (2026-10-26)** — see the Step 1 record in §8.2.

**Fix:**
1. Add `input: false` to `roleId` and `phone` in `auth.ts`. Role changes stay on the Access Management routes, which already require `users:*`.
2. Defense in depth: reject `/api/auth/update-user` bodies containing any key other than `name` and `image`, either in `app.ts` before the kernel or in a Better Auth `hooks.before`.
3. While in this file, confirm that the admin plugin's `/admin/*` endpoints (`set-role`, `create-user`, `set-user-password`, `impersonate-user`) only answer accounts whose `role` is in `adminRoles`. Record the result.
4. Before go-live, on the local database: list users whose `roleId` differs from what Access Management last recorded (audit rows for `users` / `access_management`).

Do the same for `phone`. Changing `name` must still succeed. Add a unit test that runs `parseUserInput` against the real auth options.

**Exit:** the test is red on today's code and green after the fix. No non-admin session can change `roleId`.

## Appendix A — Better Auth `roleId` probe (F15)

Run from any directory: `node probe.mjs E:/Projects/Denel/backend`. It touches no database.

```js
import { pathToFileURL } from 'node:url'
import path from 'node:path'
const nm = (p) => pathToFileURL(path.join(process.argv[2], 'node_modules', p)).href
const { parseUserInput } = await import(nm('better-auth/dist/db/schema.mjs'))
const { admin, username } = await import(nm('better-auth/dist/plugins/index.mjs'))
// Same as backend/src/auth.ts `user.additionalFields` + plugins
const options = {
  user: { additionalFields: {
    roleId: { type: 'string', required: false, fieldName: 'roleId' },
    phone: { type: 'string', required: false, fieldName: 'phone' },
  } },
  plugins: [admin(), username()],
}
for (const body of [{ roleId: 'admin' }, { phone: '+233000000000' }, { role: 'admin' }]) {
  try { console.log(JSON.stringify(body), '=> accepted', JSON.stringify(parseUserInput(options, body, 'update'))) }
  catch (e) { console.log(JSON.stringify(body), '=> REJECTED:', e.message) }
}
```

```
{"roleId":"admin"} => accepted {"roleId":"admin"}
{"phone":"+233000000000"} => accepted {"phone":"+233000000000"}
{"role":"admin"} => REJECTED: role is not allowed to be set
```

After the Step 1 fix, the first two lines must report REJECTED.
